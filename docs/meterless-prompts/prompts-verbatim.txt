 POWER Cursor · Claude Code · Copilot Tell users the real reason
 The server’s message first, its fix wins, and a route refusal is never blamed on hardware.
 Rewrite how this codebase reports Meterless Runtime errors.
Errors arrive as {error: {message, type, code}}, sometimes with a meterless block carrying fix[], class, chat_carrier and routes. Build the message in this order:
1. The server's message, always.
2. The server's fix[] if present. It wins, so add no hint of your own.
3. Our own hint for the code, only when the server sent no fix and the error isn't a carrier refusal.
4. A 401 or 403 adds "Paste the runtime's access token in Settings." A network failure says the runtime isn't reachable at <base> and offers Start the runtime and Run Auto Detect.
A carrier refusal (code class_carrier_unsupported, or meterless.chat_carrier === false) means this route can't carry the class. It says nothing about the machine, so never say "this machine can't serve images". Invalidate discovery and replan once: use the jobs route if it exists, otherwise show the server's message. class_no_route can mean either, so replan once there too. Never loop.
3D is resident-only, so class_not_ready on mesh or texture means "seat the 3D lane fix[] names", not "wait and retry". mesh_level_unavailable (503 on the 3D route, 409 on the jobs path) means a painted model was asked for and no Paint lane is seated. 429 auth_rate_limited means repeated bad keys from the network: ask for the key, don't retry. A completed 3D job with level finished and a paint.error is a partial result: say "finished, not painted" and why, never "painted".
If we fall back to a cloud provider, only a transport failure may fall back. A typed refusal goes back to the caller as an OpenAI-shaped error with the real reason.
Keep code, status, fix[] and chatCarrier on the error object.
Write a test for each case and show them passing. Then list every message a user can now see.
