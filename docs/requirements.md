# Requirements: what Barthelona must be able to do

Status: draft for owner review, 2026-10-18. Reviewed before Phase 1 starts. Docs only; no code changed.

The plan grew bottom-up: assembler adapters, a ladder, a gateway. This page works top-down. It takes the **hardest version of each demo** as a reference workload, derives the capabilities Barthelona needs to build it, and checks each against the architecture (`docs/architecture.md`, "§"), the ADRs (`docs/adr/`) and the roadmap (`docs/roadmap.md`).

Legend for status:

- **covered**: exists in `src/` and has tests.
- **planned**: designed in an ADR, the architecture or the roadmap, or filed as an issue with a phase; not built.
- **missing**: nothing in the plan. Each has an `agent-system-gap` issue (new ones are listed in section 6).

"Planned" is not "will work". Every planned row still has to pass its phase review (D-037).

## 1. Reference workloads

The demo repos ([network](https://github.com/lopatnov/barthelona-network-demo), [GUI](https://github.com/lopatnov/barthelona-gui-dektop-demo), [2D game](https://github.com/lopatnov/barthelona-2d-game-demo), [3D game](https://github.com/lopatnov/barthelona-3d-game-demo), and [simplest](https://github.com/lopatnov/barthelona-simplest-demo)) hold only a title and a licence today (checked 2026-10-18), so these definitions are mine. They are the *hardest credible version*, the bar for architecture reviews. Easier versions are steps on the way (section 5). Items marked **[owner]** are decisions in section 7.

| ID | Workload (demo repo) | Hardest version | What makes it hard |
| --- | --- | --- | --- |
| NET | Network (`barthelona-network-demo`) | Reverse proxy for files and API requests: HTTP/2 with HPACK, TLS 1.3, all crypto in assembly, no linked TLS or crypto library (D-054, PR #187) | tens of thousands of lines, many modules, crypto correctness and timing, protocol interop, sockets and event loop, fuzzing |
| GUI | Desktop GUI (`barthelona-gui-dektop-demo`) | A native desktop application (for example a task scheduler with lists, forms, text input, a settings dialog) that a person can install and use, in assembly talking to the OS windowing protocol directly **[owner: O-1]** | event-driven code, windowing and font rendering, screenshots as the only visible result, usability, packaging |
| 2D | 2D game (`barthelona-2d-game-demo`) | A real-time 2D game with sprites, animation, input, sound and levels, software-rendered or via a toolkit | frame loop, determinism, assets, "fun" and looks are not machine-decidable |
| 3D | 3D game (`barthelona-3d-game-demo`) | A real-time 3D scene or game; **[owner: D-050 puts commercial-grade 3D out of range]** | math and SIMD, rendering, assets (models, textures), performance, no GPU in the sandbox |
| CLI | Simplest (`barthelona-simplest-demo`) | The temperament test done properly: regenerated by Barthelona from a human-style prompt, with docs, CI, release, run report and provable scoring | the demo rule (AGENTS.md "Demos are Barthelona's output"); usability (F-70) |

Standing goals applied to all five (owner, 2026-10-18; project memory): built from a human-written prompt or a task repo; mostly local models spread over several PCs with hardware awareness; learnable from run data (Unsloth); documents, tests, linters, fuzzing, static analysis and CI in generated projects; reproducible with recorded inputs and statistics; registries instead of enums.

## 3. What the matrix says

1. **The network workload is already analysed.** The pure-assembly TLS and HTTP/2 proxy produced #179 to #186 (PR #187: D-054, D-055, Phase 7, F-87 to F-94). This page adds nothing new for it except dependencies on rows that other workloads need too: C6 (syscall-heavy testing), C12 (performance), A6 (context scale), B3, B4.
2. **The GUI, 2D and 3D demos have no home in the plan.** Phase 6 has C, web and a 2D game; D-050 says 3D "stays out of range" and says nothing about native GUI. Five new gaps (C14, C15, D4, D9, E1) sit between those demos and the current plan, and the review page cannot show a result a person must *look at*.
3. **Interactive and syscall-heavy programs cannot be tested by the current oracles.** V4 allows `write` and `exit`; V5 passes integers; V6 feeds stdin. A server, a window loop or a game loop needs a syscall virtualisation and trace layer (C6) with deterministic time, randomness and input (C13). This is the biggest hidden dependency: NET, GUI, 2D and 3D all need it.
4. **Measurement of progress is missing.** The bench has ten integer functions. Nothing tells the owner whether Barthelona is one step or fifty from the reference workloads, or what each PC can handle (B4). Section 5 proposes tiers.
5. **Performance is not an oracle.** Throughput, latency and frame time decide whether a proxy or a game is acceptable (C12).
6. **Scheduling ignores the owner's PC limits.** The laptop overheated during the bake-off; D-052 measures speed only (B3).
7. **Binary analysis stops at disassembly.** D-055 allows disassembly; decompilation has nothing (F2). The training discussion is only partly in the plan: the `gcc -S` pair source (F4) was named in the threads but is in no issue, and the corpus builders (F5) exist only as a script outside the repo.
8. **Most standing goals are planned and consistent.** A1, A7 to A11, B1, B2, B6 and C17 are issues with phases. The risk there is order, not absence (section 4).

## 4. Architecture changes needed

Ordered by when they must happen. "Before 1b" means the schema or registry freezes in Phase 1b (`docs/roadmap.md:39`), so the shape has to be decided first, even if the code lands later.

**Before Phase 1b freezes schemas (cheap now, expensive later)**

1. **Sandbox profiles are a registry entry (extends D-053).** A profile declares network (`none`, `loopback`), devices (`display`, `audio-null`), resources and mounts. A check declares the profile it needs; a family lists the profiles it may use. Today the profile is fixed text in §13.4. Needed by C14, C16.
2. **Contract kinds beyond `Symbol` (extends §4).** Reserve fields now: `secret: true` per argument (C8), a performance budget per symbol or test (C12), requirement ids (A4), and non-symbol kinds for events and routes (D-050 decision 5). `project.yaml` gets a `libs` list with pinned versions (D4) and a `profile` per test. Adding a field later means a schema version bump on every stored run (D-044).
3. **Check and tool registries must carry data kinds, not only pass/fail.** A check may return images, traces and measurements as artefacts with provenance (A9, C15, E1). Define the artefact record now.
4. **Role registry includes a vision role** (B5) and a role may declare a model capability (`vision`, `long_context`), checked at catalog load.
5. **Endpoint profile gains a scheduling policy** (B3): allowed hours, maximum sustained load, cool-down, `portable: true` for laptops. D-052's profile file is the natural home.

**Phase 1b to Phase 2**

6. **A dynamic-oracle layer** (C6, C13): a syscall virtualisation interface (virtual clock, files, network, input) implemented once for the Unicorn child and once as trace capture around `bart-run`, so V4, V5 and V6 share one deterministic world. This amends D-043's executor contract and §13.1.
7. **Project-level planning above the sprint** (A3): the unit of work becomes a module DAG with an integration order; a sprint takes one layer of it. Needs a project-level budget that spans runs (invariant 6 holds per run today).
8. **Workload bench ladder** (B4, section 5) and per-PC capability ceilings that the planner reads to size modules (extends D-052 clause 3).

**Phase 3 to Phase 6**

9. **Family axis introduced earlier than "when family two starts"** (D-050 consequences): by Phase 2 the `family` axis exists in contracts and targets, because the display and syscall layers are family-specific.
10. **Phase 6 widened:** add a native GUI family and decide the 3D scope (D9). Add C-family prerequisites: display sandbox, visual oracles, system-library linking, G4 with screenshots.
11. **Phase 7 prerequisites listed explicitly:** A3, A6 (context scale), C6, C12, C13, B3, B4 must be at least designed before Phase 7 starts; PR #187 lists only the crypto-specific items.
12. **Roadmap exit criteria tied to the demos:** each demo gets a tier on the ladder; "the demo works" is checked by the tier's bench task, not by a hand-built result (AGENTS.md demo rule).

## 5. Proposed bench ladder (B4)

Each tier is a set of tasks with frozen, independently sourced tests; a tier is passed when its tasks pass inside budget on a named PC and model. Tier names are suggestions.

| Tier | Example task | Exercises | Maps to |
| --- | --- | --- | --- |
| T0 | one function (today's bench) | codegen, fix loop | Phase 0 |
| T1 | a 3-module CLI (word count, hexdump, temperament test) | contracts, golden I/O, docs, CI | CLI demo |
| T2 | a parser with fuzzing (JSON, INI, base64) | fuzz oracle, memory safety | C10 |
| T3 | a stateful server over loopback (echo, then HTTP/1.1 static files) | syscall layer, interop tools, performance | NET step 1 |
| T4 | a crypto primitive with vectors (SHA-256, ChaCha20-Poly1305, X25519) | KAT, differential, constant time | NET step 2 |
| T5 | a window or frame loop in a virtual display (a 2D game in software rendering) | display sandbox, visual oracles, input scripts | 2D, GUI |
| T6 | HTTP/2 framing plus HPACK; TLS 1.3 handshake | spec traceability, conformance | NET step 3 |
| T7 | software 3D renderer with golden frames | FP and SIMD, performance budgets | 3D |
| T8 | the reference proxy | decomposition at scale | NET |

The ladder doubles as the capability curve for fine-tuning (A11): each tier yields training and evaluation data.

## 8. Method and limits

Sources read: `docs/architecture.md`, `docs/roadmap.md`, `docs/adr/D-001` to `D-053` (plus D-054 and D-055 from open PR #187), `AGENTS.md`, `src/barthelona/` module list, `config/models.yaml` (no vision model), all open `agent-system-gap` issues (29 at the time of writing). Demo repos were checked through GitHub: each holds a README title and, for the GUI demo, a licence.

Limits: workload definitions are assumptions until the owner confirms section 7. Prior art for GUI, game and visual testing was **not** researched here (F-72 stays open); each new issue names the survey to do before design. No version, price or date-sensitive fact is asserted beyond what the cited ADRs record.
