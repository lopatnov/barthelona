# D-023: Environment: conda for the interpreter only; pip installs from hash-locked files; PowerShell scripts

- Status: Proposed
- Date: 2026-10-13
- Amended by: D-031

## Decision

environment.yml: conda-forge python=3.13 and pip; the channel list ends with `nodefaults`, which keeps the defaults channel out (equivalent to --override-channels).

Install:
- pip install --require-hashes -r requirements/<profile>.win.lock, generated by `uv pip compile --generate-hashes --python-platform x86_64-pc-windows-msvc --python-version 3.13`;
- then pip install --no-deps -e . as a separate step.

Scripts:
- scripts/create_env.ps1
- scripts/activate.ps1 (dot-sourced; uses the conda PowerShell hook if conda init was not run; sets PYTHONUTF8, WSL_UTF8, BARTHELONA_HOME, LMSTUDIO_BASE_URL, QDRANT_URL)
- scripts/run.ps1
- optional .sh twins for Git Bash or a Linux host (see D-031)

## Rationale

Every binary dependency has cp313 win_amd64 or abi3 wheels.

Python 3.15 lacks wheels for onnxruntime and ormsgpack. conda-forge lags PyPI for several packages, and mixing conda and pip solvers causes conflicts.

Hash locking is the answer to the LiteLLM-style compromise.

The editable install must be a separate step because --require-hashes rejects it.

## Alternatives considered

- Install everything from conda-forge: lagging versions; langgraph-checkpoint-sqlite is missing.
- A uv-managed venv without conda: the user explicitly wants conda.
- Python 3.12: numpy 2.5 needs ≥3.12, but 3.13 is fine and current.
